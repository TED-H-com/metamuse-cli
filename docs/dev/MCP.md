# MetaMuse MCP Stdio Server (`src/metamuse/mcp.py`)

This document describes the B14 Model Context Protocol (MCP) stdio server implementation for MetaMuse (`FR-001`, `FR-018`, `AT-026` stdio subset).

---

## 1. Entry Point and Shared Application Seam

The MCP server runs in-process over standard input/output when invoked via:

```bash
metamuse --workspace <path> mcp
```

`cli.py` constructs an `app.AppContext` (`store`, `jobs`, `config`, `workspace`), calls `app.register_builtin_operations()`, and delegates to `mcp.run(ctx)`. `mcp.py` contains no domain or business logic:

1. **Tool catalogue and schemas**: Loaded strictly from packaged contract data (`importlib.resources.files("metamuse.data").joinpath("schemas", ...)` reading `mcp-tools.json` and `envelope.json`, generated by `python -m metamuse.schemas`). `mcp.py` contains no `docs/` paths and no duplicate fallback tool table.
2. **Input validation and dispatch**: Every `tools/call` invokes `app.TOOL_FUNCTIONS[name](ctx, arguments)`, the exact same `@application`-decorated entry points and `models.TOOL_REQUEST_MODELS` used by the CLI.
3. **Result envelope**: Every tool returns a single `CallToolResult` containing:
   - `structuredContent`: the serialized `Envelope` dict (`contract_version`, `request_id`, `status`, `data`, `error`, `warnings`, `next_cursor`, `approval`).
   - `content`: a single `TextContent(type="text", text=...)` carrying the identical canonical JSON serialization of that `Envelope`.
   - `isError`: `True` when `envelope.status == "error"`, `False` otherwise (`ok`, `accepted`, or `partial`).
   - When `envelope.status == "error"`, `envelope.error` includes `code`, `message`, `retry_class`, and a non-null `next_action` populated from `models.DEFAULT_NEXT_ACTIONS` whenever no explicit `next_action` is supplied, keeping CLI `--json` and MCP envelopes identical.

## 2. SDK and Protocol Version

- **Dependency**: `mcp==2.3.0` (`mcp-types==2.3.0`, MIT License).
- **Negotiated protocol version**: `2025-11-25` (`mcp.client.session.LATEST_HANDSHAKE_VERSION`) when paired with the official MCP Python SDK stdio client (`mcp.client.stdio.stdio_client` + `ClientSession.initialize()`).
- **Dual-era support**: `mcp.server.lowlevel.server.Server` (`serve_dual_era_loop`) supports MCP protocol versions `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25`, and `2026-07-28` (`mcp.types.LATEST_PROTOCOL_VERSION`).
- **Telemetry opt-out**: When `ctx.policy.app.telemetry_enabled` is `False` (the default), `create_server(ctx)` filters `OpenTelemetryMiddleware` by type from `server.middleware` without dropping any other middleware.

## 3. Registered P0 Tools and Annotation Table

Exactly the 15 P0 tools defined in `src/metamuse/data/schemas/mcp-tools.json` (`docs/design/contracts/mcp-tools.json`) are registered. Human-only interactive commands (`auth import`, `permit create`, `permit approve`) are never exposed as MCP tools.

Tool annotations are **advisory hints only** and are **never used for authorization**. Authorization and scope checks are enforced by the core store/policy layer.

- `readOnlyHint=True` and `idempotentHint=True` are set **only** for the 5 purely local read operations (`metamuse_inspect`, `metamuse_job_get`, `metamuse_job_list`, `metamuse_search`, `metamuse_draft_preview`).

## 4. Stdout Cleanliness

The MCP stdio transport requires that `stdout` carry **only** newline-delimited JSON-RPC 2.0 protocol messages:

1. `stdio_server()` captures the binary protocol output stream (`sys.stdout.buffer`) for the MCP transport and redirects OS file descriptor `1` onto `stderr`.
2. `_serve_stdio()` routes all Python loggers and `warnings.showwarning` to `sys.stderr` and wraps `await server.run(...)` in a single `redirect_stdout(sys.stderr)` context for the entire server run, avoiding any per-call worker-thread mutation of `sys.stdout`.
3. Any `print(...)`, `sys.stdout.write(...)`, `os.write(1, ...)`, `warnings.warn(...)`, root/module `logging` output, or uncaught traceback from feature code or third-party libraries is routed to `stderr`.

## 5. Explicit State Handles and Job Cancellation Semantics

1. **No implicit session state**: The MCP server holds no per-connection "current project", "current discussion", or "current draft". Every tool call must pass `project_id`, `job_id`, `discussion_id`, `exchange_id`, or `draft_id` explicitly as defined by its request schema. Creating a project with `metamuse_project_create` never sets a default `project_id` for subsequent calls.
2. **Client cancellation vs. job lifecycle**: Each `tools/call` executes the synchronous application handler in a worker thread (`anyio.to_thread.run_sync(..., abandon_on_cancel=True)`). If an MCP client cancels or abandons an in-flight `tools/call` request, the server never cancels an already-accepted background job in SQLite. Only an explicit `metamuse_job_control` call with `operation="cancel"` transitions a job to `cancelled`.

## 6. Attached Worker and Remaining Items

- **Attached worker**: `metamuse mcp` starts the existing Executor in one process-owned thread by default; `--no-worker` opts out. It acquires the same workspace OS lock as `worker run` and `add --run`, increments the same epoch, and runs existing recovery. There is no extra scheduler or service.
- **Lock contention**: A server that cannot acquire the lock continues serving with `worker_available:false`, `attached_worker:"lock_busy"` and `worker_next_action`. It does not retry acquisition during this server lifetime. Restart it after the live owner exits or run `worker run`; it never takes over a held lock. MCP reports availability of its own attached worker, even when a separate owner is working. CLI doctor reports the actual OS-lock owner across processes.
- **Availability**: Accepted envelopes have true only while this attached worker thread runs and holds the lock. Disabled/stopped/failed workers report false. Inspect includes that state and the next action. Accepted means committed, never completion or continuation after server exit.
- **Shutdown**: stdin EOF, SIGTERM and SIGINT request_stop before teardown, stop new step claims and join the current bounded step at its existing safe completion/cancel/epoch boundary before releasing the lock. Shutdown does not automatically cancel jobs. A hung dependency may delay graceful exit until its configured bound; a crash/SIGKILL leaves original recovery to the next Executor. External submits become uncertain and require history reconciliation, never automatic resend.
- **Approvals**: A missing/unusable Muse grant returns E_SCOPE_REQUIRED and a non-secret approval preview via the shared app wrapper. The host shows its exact operator command to a human; it cannot run approval through MCP. Packet preparation includes the full fixed pre-share preview; replaying that same request previews the same packet without creating another packet.
- **MCP resources**: Resource endpoints (`resources/list`, `resources/read`) are not registered; all P0 interactions go through the 15 tools.
- **External MCP host pairing**: Live host configuration and pairing with Claude Code, Codex, Grok, or Antigravity are deferred to a separately authorized round.

## 7. Safe exception logs

`call_tool` still returns a fixed `E_STORAGE` envelope for workspace I/O errors and for any other unexpected exception. Both branches log through `safe_log.log_safe_exception`. The line names the tool, `E_STORAGE`, the envelope request id, a `job_id` argument only when it already matches `job_` plus 32 hex characters, the exception class names along `__cause__` and `__context__`, and stack frames as `file:line:function`. It does not log `str(exc)`, `repr(exc)`, exception arguments, locals, or source lines. `logger.exception` and `exc_info=True` are not used.
